# Adding a New Feature

Use this page when adding a feature manually or adapting code generated by `scaffoldFeature`.

For the generator workflow, start with [Scaffold a Feature](../guides/scaffold-feature.md).

## Recommended path

Most features should start from the scaffold task:

```bash
./gradlew scaffoldFeature -PfeatureName=settings
```

Use database starter files only when the feature needs local Room persistence:

```bash
./gradlew scaffoldFeature -PfeatureName=settings -PwithDatabase=true
```

## Expected module structure

Every feature should follow the standard four-module shape:

```text
feature/{name}/
├── data
├── domain
├── navigation
└── presentation
```

## Responsibilities

| Module | Responsibility |
|---|---|
| `data` | repository implementations, DTOs, remote/local data sources |
| `domain` | repository contracts, use cases, domain models |
| `navigation` | route objects and navigation metadata |
| `presentation` | ViewModels, UI state, events, Compose screens, screen providers |

## Manual checklist

If you create or heavily modify a feature manually, verify:

- [ ] `settings.gradle.kts` includes all feature submodules.
- [ ] `app/build.gradle.kts` wires the feature modules needed by the app.
- [ ] `data` depends on `domain`.
- [ ] `presentation` depends on `domain` and `navigation`.
- [ ] `domain` does not depend on `data` or `presentation`.
- [ ] route definitions live in `navigation`.
- [ ] screen rendering lives in `presentation`.
- [ ] screen provider binding is registered through Hilt multibinding.
- [ ] DTOs do not leak into UI state.
- [ ] tests are added for real behavior.

## Validation

Run at least:

```bash
./gradlew :feature:settings:presentation:compileDebugKotlin
./gradlew ktlintCheck detekt testDebugUnitTest
```

For database-backed features, also compile the data module:

```bash
./gradlew :feature:settings:data:compileDebugKotlin
```
