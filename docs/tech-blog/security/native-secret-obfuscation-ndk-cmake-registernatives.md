# Native Secret Obfuscation with NDK, CMake and RegisterNatives

## Who this article is for

This article is for Android developers who need a realistic understanding of client-side secret handling. It is especially useful for developers building templates, SDK-like apps, or apps with release hardening requirements.

## What you will learn

- Why client-side secrets are never truly secret
- Why `BuildConfig` is easy to extract
- What native obfuscation can and cannot protect
- How NDK and CMake fit into Android builds
- Why `RegisterNatives` is safer for package-renamable templates
- Production checklist and threat model

## The uncomfortable truth

If a value must be available on the client, a determined attacker can eventually recover it.

That includes:

- API keys used by the app,
- base URLs,
- certificate pins,
- feature flags,
- local encryption metadata.

Client-side hardening is not about making extraction impossible. It is about reducing accidental leakage, raising extraction cost, and making abuse harder when combined with backend controls.

## Why BuildConfig is not enough

Android projects often put values into `BuildConfig`:

```kotlin
BuildConfig.API_KEY
```

This is convenient, but it can expose values as readable strings in generated bytecode or decompiled output.

For non-sensitive constants, that is fine. For values that should not be casually extracted, it is weak.

## Native obfuscation mental model

Native obfuscation moves value reconstruction into C/C++ code compiled into a native library.

This can:

- avoid obvious Kotlin string constants,
- make static extraction harder,
- combine values at runtime,
- apply simple transformations such as XOR masking.

It does not create a real secret boundary. Attackers can still inspect native code, hook calls, dump memory, or instrument the process.

## NDK and CMake in Android

The Android NDK lets you compile native C/C++ code into `.so` libraries.

CMake describes how native sources are built and how build-time arguments are passed.

In ComposeTemplate, native secret handling lives in `core:secrets`, with CMake and native source files participating in the Android build.

## Why templates have an extra JNI problem

JNI has a common convention-based lookup format:

```text
Java_com_example_app_ClassName_methodName
```

That is fragile in a template generator. If the generated app changes package name, convention-based native method names can break.

A template must survive package rebranding.

## RegisterNatives

`RegisterNatives` avoids depending on convention-based method names. Instead, native methods are registered programmatically when the library loads.

Conceptually:

```cpp
JNI_OnLoad(JavaVM* vm, void*) {
    // find target class
    // register native method table
}
```

This allows the target class path to be injected from build configuration, which is important when `create-new-app` rewrites package names.

## ComposeTemplate approach

ComposeTemplate combines:

- `core:secrets`,
- Android NDK,
- CMake,
- native value reconstruction,
- Gradle convention plugin setup,
- `JNI_OnLoad` and `RegisterNatives`,
- validation and artifact scanning tasks.

Relevant areas:

- `core/secrets/`
- `core/secrets/src/main/cpp/`
- `build-logic/convention/AndroidLibraryNativeConventionPlugin.kt`
- `build-logic/convention/ValidateSecretsPlugin.kt`

## Threat model

This protects mostly against:

- casual APK inspection,
- accidental plain string exposure,
- release misconfiguration,
- simple grep-based extraction.

It does not protect against:

- dynamic instrumentation,
- rooted device inspection,
- memory dumping,
- backend abuse,
- replay or credential theft after runtime extraction.

## Best practices

- Never put real backend master secrets in an app.
- Restrict API keys server-side.
- Use certificate pinning carefully when appropriate.
- Validate release config before building.
- Scan artifacts for known raw values.
- Treat runtime integrity checks as signals, not guarantees.

## Common mistakes

### Overselling client-side secret protection

Native obfuscation is hardening, not secrecy.

### Breaking generated apps after package rename

Convention JNI names can break when templates are rebranded.

### Relying only on obfuscation

Backend authorization and rate limiting still matter.

## Production checklist

- [ ] No production master secrets are stored in the app.
- [ ] API keys are restricted server-side.
- [ ] Native bindings survive package rename.
- [ ] Release secrets are validated before build.
- [ ] APK/AAB artifacts are scanned for raw values.
- [ ] Security documentation explains limitations honestly.

## Summary

Native secret obfuscation raises the cost of extraction and reduces accidental leakage, but it is not a security boundary.

ComposeTemplate uses NDK, CMake and `RegisterNatives` because templates need a hardening approach that survives generated package names and avoids obvious string exposure.
