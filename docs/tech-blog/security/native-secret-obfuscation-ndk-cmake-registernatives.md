# Native Secret Obfuscation with NDK, CMake and RegisterNatives

## Who this article is for

This article is for Android developers who need a realistic model for client-side secret hardening.

## What you will learn

- Why client-side secrets are never truly secret
- Why `BuildConfig` is easy to inspect
- What native obfuscation can and cannot do
- How NDK, CMake, JNI, and `RegisterNatives` fit together
- Why template generators need package-rename-safe native bindings

## The uncomfortable truth

If a value must exist on the device, a determined attacker can recover it. Client-side hardening is about raising cost, reducing accidental leakage, and combining signals with backend controls.

Never put backend master secrets in a mobile app.

## Why BuildConfig is weak for secrets

`BuildConfig` is convenient, but values can be visible in generated bytecode or decompiled output:

```kotlin
BuildConfig.API_KEY
```

For non-sensitive configuration, this is acceptable. For values that should not be casually extracted, it is weak.

## Native obfuscation mental model

Native obfuscation moves value reconstruction into compiled C/C++ code. It can avoid obvious Kotlin constants and make static extraction harder.

It does not stop dynamic instrumentation, memory dumping, or runtime hooks.

## NDK and CMake

The Android NDK compiles native code into `.so` libraries. CMake defines how that native code is built and can receive build-time arguments from Gradle.

ComposeTemplate uses `core:secrets` for native-backed secret hardening.

## Why RegisterNatives matters

Traditional JNI names depend on package/class names:

```text
Java_com_example_app_SecretReader_getApiKey
```

A template generator changes package names. That can break convention-based JNI methods.

`RegisterNatives` registers native methods programmatically from `JNI_OnLoad`, allowing the target class path to be supplied by build configuration.

## Threat model

This helps against:

- casual APK inspection
- simple string extraction
- accidental raw value leakage
- placeholder release mistakes

It does not protect against:

- rooted runtime inspection
- Frida/hooking
- memory dumps
- backend abuse
- stolen runtime tokens

## ComposeTemplate approach

Relevant pieces include:

- `core/secrets/`
- `core/secrets/src/main/cpp/`
- `AndroidLibraryNativeConventionPlugin.kt`
- `ValidateSecretsPlugin.kt`

The native layer is one part of a broader hardening story that also includes validation, artifact scanning, certificate pinning, and runtime integrity signals.

## Production checklist

- [ ] No real backend master secret is stored in the client.
- [ ] API keys are restricted server-side.
- [ ] Native bindings survive package rename.
- [ ] Release values are validated.
- [ ] APK/AAB artifacts are scanned.
- [ ] Documentation explains limitations honestly.

## Summary

Native obfuscation is a cost-increasing layer, not a security boundary. ComposeTemplate uses NDK, CMake, and `RegisterNatives` because template-generated package names need native bindings that remain stable after rebranding.
