# Native Secret Obfuscation with NDK, CMake and RegisterNatives

## Who this article is for

This article is for Android developers who need a realistic model for client-side secret hardening.

## What you will learn

- why client-side secrets are never truly secret
- why `BuildConfig` is easy to inspect
- what native obfuscation can and cannot do
- how NDK, CMake, JNI, and runtime validation fit together
- why generated package names must not break native bindings

## The problem

Mobile clients sometimes need API keys, base URLs, feature configuration, or integrity parameters at runtime. Placing those values directly in Kotlin constants or `BuildConfig` is convenient, but easy to inspect in decompiled output.

The uncomfortable truth is that anything shipped inside an APK/AAB can eventually be recovered. The goal is not perfect secrecy. The goal is to reduce accidental leakage and increase extraction cost.

## Why this matters for Android projects

Client configuration mistakes can weaken production releases:

- placeholder keys reach release
- debug base URLs ship accidentally
- raw keys appear in artifacts
- runtime checks are disabled unintentionally
- package rename breaks native access

A production template should provide guardrails for all of these.

## Common approaches

### Plain `BuildConfig`

Simple and useful for non-sensitive configuration, but values may be visible in generated bytecode or decompiled output.

### Remote config only

Useful for dynamic behavior, but not a security boundary if the client can be modified.

### Native-backed reconstruction

Moves value reconstruction into compiled native code. This raises static extraction cost, but does not stop dynamic instrumentation or memory inspection.

## ComposeTemplate's approach

ComposeTemplate uses `core:secrets` and native build configuration to support native-backed secret access.

`SecretManager` loads the native library when native secrets are enabled:

```kotlin
if (BuildConfig.NATIVE_SECRETS_ENABLED) {
    System.loadLibrary("native-lib")
}
```

It exposes API key, base URL, expected signature hash, runtime-check flags, and certificate pinning configuration.

## Runtime validation

Returned values are validated before use. For example, base URLs must use HTTPS outside debug builds and end with `/` because Retrofit requires a trailing slash.

If a native integrity check blocks access and returns an unauthorized value, `SecretManager` fails fast.

## RegisterNatives and package rebrand safety

Traditional JNI exports encode the Java package name. Template generators rename packages, which can break convention-based JNI method names.

A package-rename-safe native layer should avoid relying on generated Java-style native names. Registering native methods programmatically keeps generated apps safer during rebrand.

## Threat model

This helps against:

- casual APK inspection
- obvious string extraction
- accidental raw-value leakage
- placeholder release mistakes

It does not stop:

- rooted runtime inspection
- Frida or hooking
- memory dumping
- backend abuse
- stolen tokens

## Design trade-offs

Native hardening adds NDK/CMake complexity and can make builds harder to debug. ComposeTemplate accepts this because the feature is optional and documented as a hardening layer, not a guarantee.

## Production checklist

- [ ] no backend master secret is stored in the client
- [ ] native secret mode is intentionally enabled or disabled
- [ ] base URLs validate correctly
- [ ] generated package names do not break native access
- [ ] release values pass `validateSecrets`
- [ ] artifacts pass `scanApkForSecrets`
- [ ] backend restrictions exist for client-exposed keys

## Takeaways

- Native obfuscation increases cost; it does not create perfect secrecy.
- Release validation is as important as obfuscation.
- Template generators must design native bindings for package rename safety.
